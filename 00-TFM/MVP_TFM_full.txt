Ahora voy punto por punto, a nivel técnico.
1) Transformer multimodal BEV para percepción


Qué es exactamente


Aquí la idea es construir un modelo de percepción que tome sensores
heterogéneos:

    cámaras RGB

    LiDAR

    radar

    IMU/GNSS/odometría como contexto ego


y los convierta en una representación común en BEV (Bird’s-Eye View), es decir,
una vista cenital del entorno.

Esa representación BEV es muy potente porque:

    la planificación trabaja naturalmente en coordenadas top-down,

    la geometría del vehículo y del apero se expresa mejor en planta,

    es más fácil razonar sobre:

            ocupación

            espacio libre

            obstáculos

            pasillos

            líneas de cultivo

            zonas no transitables.



La revisión reciente sobre transformers en conducción autónoma destaca
precisamente su utilidad en percepción, fusión sensorial, predicción y motion
planning, resaltando ventajas frente a CNN/RNN en contexto global y alineación
multimodal ScienceDirect.


Arquitectura típica


Una implementación razonable sería tipo BEVFusion / BEVFormer-like:

 1.
      Encoder por sensor

            cámara: backbone CNN o ViT para extraer features 2D

            LiDAR: voxelization / pillarization + backbone 3D o sparse conv

            radar: representación rasterizada o puntos + encoder específico



 2.
      Proyección a marco común

            las features de cámara se proyectan al espacio 3D/BEV usando
            calibración extrínseca e intrínseca

            las de LiDAR/radar ya están cerca del marco geométrico del mundo



 3.
      Fusión multimodal

            mediante cross-attention entre sensores

            opcionalmente también temporal attention para usar historial



 4.
      Heads de salida

            detección 3D de objetos

            segmentación semántica BEV

            occupancy / free-space
           estimación de transitabilidad

           predicción de objetos dinámicos

Para maquinaria agrícola autónoma, yo pediría al modelo estas salidas:

    occupancy grid o mapa de ocupación

    free-space map

    detección 3D de:

           árboles

           vehículos

           remolques

           postes

           maquinaria



    segmentación de suelo

           transitable

           no transitable

           vegetación alta

           cultivo

           borde de camino

           cabecera
    incertidumbre/confianza

    opcional:

           drivable corridor

           estimación de borde de surco o línea de trabajo.




Por qué BEV es especialmente adecuado aquí


Porque tu problema no es “ver bonito”, sino operar geometría:

    ancho de máquina

    ancho de apero

    radio de giro

    barrido trasero

    distancia de seguridad

    ocupación efectiva del conjunto tractor + implemento.

En BEV todo eso se modela mucho mejor que en imagen frontal pura.


Qué tipo de machine learning se emplea


Aquí la respuesta principal es:

    Deep Learning

    normalmente Supervised Learning

y secundariamente:

    Self-Supervised Learning o pretraining multimodal, si quieres mejorar robustez
    con mucho dato no etiquetado
    algo de Semi-Supervised Learning, si el etiquetado completo es caro.


Pero el núcleo productivo suele ser supervisado.


Cómo se entrena


Con datos sincronizados y calibrados, y etiquetas como:

    cajas 3D

    máscaras BEV

    ocupación

    clases semánticas

    trayectorias de objetos

Pérdidas típicas:

    clasificación: focal loss / cross entropy

    regresión de cajas: L1 / smooth L1 / IoU-like

    segmentación: CE + Dice

    occupancy: BCE / focal

    temporal consistency loss si metes memoria


Ventajas técnicas


    captura contexto espacial global

    fusiona sensores muy distintos

    tolera mejor oclusiones parciales

    produce un mapa topológico útil para planificación
    puede incorporar historia temporal


Inconvenientes reales


    requiere sincronización y calibración muy finas

    coste computacional alto

    BEV denso puede penalizar FPS y memoria; eso también lo comenta trabajo
    reciente sobre arquitecturas end-to-end con BEV denso OpenReview

    en campo tendrás problemas de:

           polvo

           vibración

           suciedad en cámara/LiDAR

           GNSS degradado bajo arbolado.




Mi recomendación concreta


Para tu caso, este es el modelo más importante del sistema.

Si hay que priorizar, este va primero.


Tipo ML resumido


    Principal: Supervised Deep Learning

    Secundario útil: Self-supervised pretraining / semi-supervised

    No principal: Reinforcement Learning


2) Planificación híbrida: ML + planner clásico + MPC

Este punto es muy importante entenderlo bien: no es un solo modelo ML.
Es un sistema híbrido donde cada parte hace algo distinto.


Qué problema resuelve


Dado:

    un mapa BEV / occupancy

    estado del vehículo

    objetivo o misión

    restricciones geométricas y dinámicas


quieres obtener una trayectoria que sea a la vez:

    segura

    factible cinemáticamente

    eficiente

    suave

    ejecutable por el controlador.


Por qué no recomiendo “solo ML”


Porque planificación en maquinaria pesada tiene restricciones duras:

    no colisionar

    respetar radio de giro

    respetar límites de dirección

    controlar derrape/patinamiento

    no invadir zonas prohibidas

    no generar maniobras imposibles con remolque o apero.
Un modelo puro aprendido puede proponer trayectorias “parecidas” a las humanas,
pero fuera de distribución puede hacer cosas absurdas.

Por eso la mejor arquitectura práctica es:

 1. ML propone o puntúa

 2. planner clásico verifica/genera candidatos

 3. MPC ejecuta respetando restricciones


Descomposición técnica correcta



A. Capa global



Se encarga de:

    cobertura de parcela

    secuencia de pasadas

    orden de tareas

    waypoints globales

    minimizar solapamientos y maniobras inútiles


Aquí normalmente no usaría ML como núcleo.

Usaría algoritmos clásicos de:

    coverage path planning

    optimización sobre grafo

    descomposición tipo boustrophedon

    heurísticas con coste operativo


Esto no es Machine Learning. Es optimización clásica / planificación algorítmica.
B. Capa local



Se encarga de:

    esquivar obstáculos

    recalcular a corto horizonte

    elegir entre varias maniobras

    decidir si seguir, frenar o parar seguro


Aquí sí tiene sentido meter una parte aprendida.

Ejemplos:

    red que genere trayectorias candidatas

    red que puntúe trayectorias

    learned cost map

    trajectory transformer

    diffusion policy para maniobras cortas

    imitation learning a partir de conducción experta


C. Capa de validación física/seguridad



Esta capa comprueba:

    colisión

    límites cinemáticos

    geofence

    viabilidad con el apero

    márgenes de seguridad
    reversa o maniobra admisible


Aquí usaría:

    Hybrid A*

    lattice planner

    collision checker

    restricciones geométricas del vehículo-articulación


D. Control de seguimiento



Una vez elegida la trayectoria, toca ejecutarla.

Aquí entra MPC.

MathWorks resume bien el rol de MPC: resolver un problema de optimización sobre
un horizonte, con restricciones explícitas, tanto lineales como no lineales,
aplicándolo a planificación de rutas, seguimiento y otras tareas de conducción
autónoma MathWorks.


Qué hace el MPC exactamente


El Model Predictive Control usa un modelo del vehículo para predecir su evolución
futura y resolver, en cada ciclo, una optimización:


    minimiza error respecto a trayectoria

    penaliza cambios bruscos de control

    respeta restricciones:

            dirección

            velocidad

            aceleración

            curvatura
             estabilidad

             distancia a obstáculos

             límites del actuador

Ojo importante: MPC no es ML


Esto conviene dejarlo nítido.


    MPC no es machine learning

    es control óptimo / optimización online basada en modelo

Puede coexistir con ML, pero no pertenece a supervised/unsupervised/RL.


Entonces, ¿qué “modelo de ML” hay aquí?


Depende de qué parte híbrida quieras aprender.

La opción más sólida para un MVP serio es:

    ML para propuesta o scoring de trayectorias

    clásico para seguridad y factibilidad
    MPC para ejecución

El ML aquí suele ser:

    Supervised Learning mediante Imitation Learning

    implementado con Deep Learning

Ejemplos de entrenamiento:

    entrada:

              occupancy map

              estado ego

              objetivo local

              historial reciente



    salida:

              trayectoria futura

              distribución sobre maniobras

              ranking de candidatos




¿Se puede usar Reinforcement Learning?


Sí, pero yo no lo pondría como primera opción en producción.

RL puede servir para:

    afinar maniobras

    optimizar eficiencia

    aprender estrategias en simulación
    fine-tuning local

Pero en sistemas reales de maquinaria pesada tiene pegas:

    sample inefficiency

    difícil garantizar seguridad

    sim2real complicado

    comportamiento impredecible fuera del dominio.

Mi criterio:

RL como herramienta secundaria, no como núcleo del MVP.


Diseño que yo recomendaría

    Local planner: red supervisada o imitation learning para generar/scorar
    maniobras

    Safety layer: clásica, obligatoria

    Trajectory tracking: NMPC o MPC

3) Pose estimation para aperos


Qué problema resuelve exactamente


Aquí ya no estás en navegación general, sino en manipulación geométrica fina.

Ejemplos:

    alinear tractor con remolque

    alinear cosechadora con peine

    aproximar enganche a bulón/punto de acople

    saber orientación relativa apero-vehículo
    controlar error lateral, longitudinal y angular en maniobra lenta.

Esto exige estimar con precisión la pose relativa del apero respecto al vehículo o
cámara.


Qué significa pose estimation aquí


En términos técnicos, suele ser estimación de pose 6D:

    3 componentes de traslación

    3 de rotación

Es decir, calcular la transformación rígida:

T = [R, t]
que lleva del sistema de coordenadas del apero al de la cámara o al vehículo.

Esa es precisamente la definición estándar de 6D object pose estimation GitHub
6D Pose Estimation.


Arquitectura práctica para aperos


La pipeline típica sería:

 1. detección del apero / punto de enganche

 2. segmentación o keypoints

 3. estimación de pose 6D

 4. refinamiento geométrico

 5. visual servoing / control fino


Enfoques que sí encajan



Opción 1: Keypoint detection + geometría
La red detecta puntos clave:

    boca de enganche

    bulón

    extremos del apero

    referencias visuales rígidas


Luego, con la geometría conocida del apero, resuelves pose con PnP o equivalente.

Esto es muy útil cuando:

    tienes aperos conocidos

    puedes definir puntos semánticos claros

    quieres interpretabilidad


Opción 2: Instance segmentation + pose regression



La red primero segmenta el apero y luego estima directamente:

    traslación

    orientación


Puede funcionar bien cuando la forma visual es bastante consistente.


Opción 3: RGB-D / point cloud 6D pose



Si montas cámara de profundidad o LiDAR cercano, puedes estimar pose sobre
nube de puntos.

La recopilación de métodos de 6D pose muestra justo esa división entre métodos
basados en:


    RGB-D
    point cloud

    semantic keypoints

    segmentation-driven

    point-based networks GitHub 6D Pose Estimation


Qué sensores usaría


Para esta tarea concreta, yo usaría:

    cámara cercana trasera o lateral trasera

    idealmente RGB-D o estéreo si el presupuesto lo permite

    iluminación controlada si es posible

    IMU/odometría como apoyo

    opcional fiducials si quieres acelerar MVP


Qué tipo de machine learning se emplea


Aquí el tipo principal vuelve a ser:

    Supervised Learning

    dentro de Deep Learning

Modelos típicos:


    CNNs de keypoints

    redes de segmentación

    redes de regresión de pose 6DoF

    PointNet/Point Transformer-like si usas nube de puntos

    refinamiento iterativo
También es muy útil:

    Self-Supervised / Weakly Supervised para aprovechar sintético + pocas
    anotaciones reales

    domain randomization en simulación


Qué no usaría como núcleo


    Unsupervised puro: no suele ser suficiente para precisión industrial

    RL como núcleo de pose: no; RL sería para la política de maniobra, no para
    estimar pose


Salidas necesarias


No basta con “detectar el apero”.

Necesitas al menos:


    posición relativa x, y, z

    orientación relativa (roll, pitch, yaw) o representación equivalente

    confianza de estimación

    visibilidad/oclusiones

    error estimado de alineación


Por qué esto no iría en el MVP inicial


Porque exige:

    dataset muy específico

    instrumentación y etiquetado fino

    maniobras lentas y seguras
    tolerancias pequeñas

    integración estrecha con control

Además, la suciedad, vibración, barro y oclusiones te afectan muchísimo más aquí
que en navegación abierta.

Por eso tiene sentido dejarlo para fase 2 o 3 si quieres acortar plazos.


Mi recomendación concreta


Si lo haces, yo iría por:

    detección/segmentación del apero

    keypoints semánticos

    estimación de pose 6D

    refinamiento geométrico

    control visual lento con safety layer


Tipo ML resumido


    Principal: Supervised Deep Learning

    Complementario: Self-supervised / synthetic-to-real

    No principal: RL

    Imprescindible pero no ML: geometría 3D, PnP/ICP, visual servoing, control

Propuesta de TFM explicada al tutor

Mi propuesta de TFM es desarrollar un MVP de autonomía vehicular centrado
en dos bloques principales:

 1. Percepción del entorno en BEV mediante un modelo multimodal basado en
    Transformer

 2. Planificación híbrida de trayectorias: percepción + planner clásico + MPC

El tercer punto, pose estimation para aperos, lo dejaría como línea futura de
desarrollo, no como alcance del TFM.




1) Percepción: Transformer multimodal en BEV

Lo primero que quiero construir es una representación BEV (Bird’s-Eye View) del
entorno a partir de varios sensores, principalmente:

    cámaras RGB

    LiDAR

    GNSS/IMU/odometría

La idea es fusionar esa información en una vista cenital métrica que me permita
saber:
    qué espacio está libre

    qué espacio está ocupado

    dónde están los obstáculos

    qué zonas son transitables

    cuál es la geometría útil para planificar


Justificación técnica


La BEV es una representación muy adecuada para autonomía porque convierte el
entorno en un plano donde la planificación y el control tienen sentido físico directo.
En la literatura reciente se ve que la representación BEV mejora tareas como
percepción, segmentación del espacio transitable, localización y planificación. Por
ejemplo, BEV-ODOM justifica que la representación BEV aporta consistencia de
escala y reduce deriva en estimación de movimiento; JPerceiver muestra que
profundidad, pose y layout BEV pueden aprenderse conjuntamente; y
BEVMapMatch destaca que el BEV es especialmente útil para map understanding,
drivable-region segmentation y localización robusta.


Modelo que usaría


Aquí el núcleo sí sería claramente Deep Learning supervisado:

    Transformer multimodal

    aprendizaje principal: Supervised Learning

    apoyo posible: self-supervised pretraining o semi-supervised learning


Arquitectura propuesta


Una arquitectura razonable sería:

    encoder por sensor

           cámara: backbone CNN o ViT
           LiDAR: voxel/pillar encoder



    proyección a espacio común

    fusión multimodal

           cross-attention

           temporal attention si se usa historial



    heads de salida

           occupancy grid

           free-space map

           segmentación semántica BEV

           detección de obstáculos

           opcionalmente estimación de incertidumbre




Resultado esperado


Este bloque me debería entregar un mapa estructurado del entorno que alimente
la planificación.

En otras palabras: el sistema no “ve imágenes”, sino que “entiende el espacio
operativo”.




2) Planificación híbrida: ML + planner clásico + MPC

El segundo gran bloque del TFM sería la planificación híbrida.

Aquí el objetivo no es solo detectar el entorno, sino decidir una trayectoria segura,
suave y físicamente ejecutable.
Idea principal


No quiero hacer una planificación puramente basada en red neuronal, porque en un
sistema real eso es frágil.

La propuesta es una arquitectura híbrida donde:

    la percepción BEV aporta el estado del entorno

    un planner clásico garantiza factibilidad y seguridad

    un bloque aprendido puede ayudar a proponer o puntuar trayectorias

    un MPC ejecuta la trayectoria respetando restricciones dinámicas


Justificación técnica


Esta arquitectura es la más seria para un MVP real porque combina:

    robustez

    interpretabilidad

    restricciones físicas explícitas

    capacidad de aprovechar ML sin depender completamente de él

Además, en problemas de navegación real, el BEV encaja de forma natural con
pose 3-DoF y con planificación local sobre mapa ocupacional. La idea de usar BEV
como espacio intermedio para tareas de localización y razonamiento geométrico
aparece también en trabajos como C-BEV, BEV-ODOM y BEVMapMatch.


Cómo dividiría esta planificación



Capa global



Se encarga de:

    waypoints
    ruta general

    cobertura o secuencia de trayectorias

    objetivo global

Aquí usaría algoritmos clásicos, no ML.


Capa local



Se encarga de:

    esquivar obstáculos

    replanificar a corto horizonte

    elegir maniobra local

Aquí sí puede entrar ML, por ejemplo:

    red que puntúe trayectorias

    red que genere trayectorias candidatas

    learned cost map

    imitation learning sobre conducción experta


Capa de validación



Valida:

    colisión

    geofence

    radio de giro

    restricciones cinemáticas
Aquí usaría de nuevo métodos clásicos como:

    lattice planner

    Hybrid A*

    collision checker


Capa de control



Aquí usaría MPC para seguir la trayectoria.

El MPC me interesa porque permite optimizar online bajo restricciones explícitas:

    velocidad

    dirección

    aceleración

    curvatura

    seguimiento de referencia


Tipo de ML en este bloque


Este punto es mixto:

    parte aprendida:

           Supervised Learning

           Imitation Learning

           Deep Learning



    parte no aprendida:

           planner clásico
            chequeo geométrico

            MPC



Reinforcement Learning no sería el núcleo del TFM.

Lo dejaría, como mucho, para simulación o trabajo futuro. Hay literatura interesante
sobre RL aplicado a planificación óptima en vehículos autónomos, como esta tesis

controlable y verificable.

Quiero desarrollar un MVP de conducción autónoma centrado en percepción y
